# v3.0.4
<!-- release-title: Magisk 模块版可手动停止 / 启动面板，通知渠道新增「绑定推送」，前置脚本里的 export 终于对目标脚本生效 -->

## 版本概览

`v3.0.4` 的主题是**把「你以为本来就该这样」补回来**——三件用户默认成立、实际一直不成立的事。

模块版的面板终于可以关掉；通知终于能做到「一个脚本对应一个渠道」；任务前置脚本里的 `export` 终于真的对目标脚本生效。

## 新增

- **Magisk 模块版可以手动停止 / 启动面板**：在模块管理器点模块卡片的动作按钮即可停止面板，再点一次启动。不用重启手机，也不用关掉整个模块。

  停止状态写在模块的持久化目录里，**跨重启保持**：重启后 `service.sh` 读到停止开关就直接退出，面板不会自己起来，再点一次动作按钮才恢复。判定以进程状态为准，所以面板刚崩掉但没写过停止开关时，这一次点击执行的是「启动」。

  停止时会释放 `wake_lock` 并恢复 doze——省电本来就是按下停止的主要动机；但**容器内的 sshd 与 ruri 挂载一律保留**：面板停了 Web 就没了，SSH 是唯一的排障退路。

  面板里也加了同一个开关：「系统设置 → 概览 → 停止面板服务」，仅模块版可见。

  > 模块版用户的升级须知：本版改动了 `service.sh` / `action.sh`，但**在线升级放行的最低外壳版本仍然是 1**，所以在线升级照常放行。也就是说，一键升上来的用户拿到的是「新面板 + 旧模块脚本」：管理器里的版本号已经是 `v3.0.4`，动作按钮却还是旧版那个只读的状态面板；面板里的「停止面板服务」按钮也会检测到外壳版本低于 2 而显示为禁用并给出提示。
  >
  > **想用手动停止，必须重刷一次模块 ZIP。** 刷过之后，后续版本仍然可以一键在线升级。

- **通知渠道新增「推送范围」**：每个渠道可以选「默认推送」或「绑定推送」。

  「绑定推送」的渠道**不参与广播**，只有任务显式绑定了它才会推送——「一个脚本对应一个通知」这件事到这一版才真正做得到。此前只要渠道是启用状态，任何一条系统通知、任何一个没绑定渠道的任务都会往它发。

  > 升级后所有老渠道一律是「默认推送」，行为与升级前逐字节一致。
  >
  > 一个边界要知道：当所有启用渠道都被设成「绑定推送」时，广播**严格不发**（只在服务端日志留一行 warn），不会退化成「发给所有人」。通知页会对这种状态给出显著提示，避免出现「一条通知都收不到且毫无线索」。

## 修复

- **任务前置脚本里的 `export` 现在真的对目标脚本生效**（Python / Node / bash 都算）。

  > 根因：前置脚本一直是在**独立子进程**里跑的，子进程的 `export` 不可能影响随后启动的目标脚本——青龙的 `task_before` 是 `source` 进同一个 shell 的，所以那边天然成立。现在前置脚本执行完会把它导出的变量**增量合并**回任务环境，再交给目标脚本。
  >
  > 全局 `task_before.sh` 同样生效。`unset` 不传导（想清空请写 `export VAR=`）。
  >
  > `TZ` 和 `DAIDAI_` 开头的面板内部变量不接受覆盖：改了会静默破坏时区链路与通知投递（例如把 `DAIDAI_NOTIFY_CHANNEL_ID` 改空，通知会从「定向到绑定渠道」悄悄退化成广播）。被拦下时任务日志里会写明是哪些变量。

- 顺带说明：想「只跑环境变量的第 N 个值」，正规写法是 `desi` / `conc`，例如 `task 脚本.py desi 变量名 3`。它发生在前置脚本**之后**，两者撞上同一个变量时以 `desi` / `conc` 为准。

- **前置 / 后置脚本执行失败不再完全静默**：以前 bash 找不到、执行超时、临时文件写不进去时，任务日志里只有孤零零一行「[执行前置脚本]」，然后什么都没有。现在失败原因会直接写进任务日志。

- **模块版的存活守护不再叠加**：以前每跑一次 `service.sh` 就多 fork 一个守护循环，多个守护彼此看不见对方的冷却，会各自进容器重跑启动脚本——表现是 `config.yaml` 被覆盖、SSH 密码被改回配置值、ruri 挂载持续累积。现在用守护代次标记做到「新守护上台、旧守护自动下台」。

- **Magisk 文档里两处「立即停：`pkill -f daidai-server`」是错的**：自 `v3.0.3` 加了存活守护之后，`pkill` 掉的面板最多 60 秒就会被拉回来（刚拉起过的话最坏要等 5 分钟，看起来像是随机复活）。两处都已改成引导用户点动作按钮。

- **`POST /notifications/send` 点名了渠道却没有有效 ID 时直接 400**：传了 `channel_id` / `channel_ids`、但归一化后一个大于 0 的 ID 都不剩时，以前会静默退化成广播，响应里 `used_all` 还报告 `false`——接口在说谎。引入「绑定推送」后这条路径更危险：本想只发一个专用渠道，结果所有默认推送渠道都收到了。

  > 唯一会撞上这条的是手工把环境变量 `DAIDAI_NOTIFY_CHANNEL_ID` 设成了 `0` 的用法。空数组 `"channel_ids": []` 不算「点名」，仍然走广播，老客户端不受影响。

## 内部改动

- 模块外壳版本号拆成两个常量：`currentMagiskShellVersion`（仓库里实际发布的外壳版本，本版为 `2`）与 `requiredMagiskShellVersion`（在线升级放行的最低外壳版本，本版仍为 `1`）。以前是同一个数字，改任何一个 `Magisk/*.sh` 都会连带把所有老用户的一键在线升级挡掉。
- `GET /system/info` 新增 `deployment_type` 与 `magisk_shell_version` 两个字段，前端不必再靠「检查更新」（需要联网拉 GitHub）才能知道当前部署形态。

## 配套的 APP 版本

APP 沿用 `v1.3.1`，本轮不发新版。

`push_scope` 是新增的渠道属性，APP 的渠道编辑表单若是硬编码的，这一项只能在 Web 端设置。面板侧已经保证 APP 提交的编辑请求不会清掉该标记：`PUT /notifications/:id` 是按键更新，缺字段与显式 `null` 都视为「未提供」，不会把用户在 Web 上设的「绑定推送」悄悄改回「默认推送」。
