# v3.0.5

## 版本概览

`v3.0.5` 是一个纯修复版，四项全部来自用户反馈。共同点是**面板一直在替你做一件你没让它做的事**：订阅每拉一次就把你手改的定时打回去、开了两步验证的 APP 永远等不到那个输入框、Debian 版装依赖时容器里只有一条硬编码 DNS、`.git` 连同里面的订阅令牌一起摆在脚本管理里。

本版没有新功能。

## 修复

- **订阅拉取不再覆盖你手改的定时任务**。

  现象是这样的：新建订阅、配好定时拉取、生成任务，然后手动把某个任务的 Cron 改成自己想要的时间；下一次点【立即拉取】，定时又被重置回订阅源自带的那个值。把订阅的「强制覆盖拉取」关掉也没有用。

  > 关掉开关没用不是漏判，是**这个开关从来就没有连到任务表上**。`force_overwrite` 唯一的作用域是 git 工作区文件——决定拉取前是 `reset --hard` 还是 `stash`，跟任务的名称、定时一个字都不相干。两者本就正交，所以「试了关开关，还是被覆盖」是必然结果，而不是偶发。

  现在的行为：只要你在面板里改过某个任务的**名称或定时**，这个任务就会自动加锁，后续订阅拉取不再覆盖它，同步日志里会写明「保留手动定时」。想让它重新跟随订阅，在任务详情点「恢复为订阅默认」即可解锁。

  顺带修掉的是同一条链路上破坏力大得多的另一个问题：`autoDelete`（**默认开启**）此前在上游改了脚本文件名、或者你改了订阅的保存目录 / 别名 / 任务命令时，会把匹配不上的任务**连同全部历史执行日志物理删除**再重新建一个。现在加锁的任务不会被自动删除，同步日志会提示你手动确认。

  > **升级须知：升级后的第一次拉取仍会重置一次。** 新增的加锁标记默认是「未加锁」，存量任务全部如此。数据库里没有任何信号能区分「用户手改过」和「订阅源本来就是这个时间」，一次性批量标记会把本该跟随订阅的任务错误锁死，从此再也拉不动。
  >
  > 所以请先把定时改成你要的值——**这一步本身就会自动加锁**——之后就不会再被覆盖了。

  > 已知副作用：改订阅的**保存目录或别名**会让仓库里所有脚本的相对路径整体变化，于是新路径照常建任务、旧路径上已加锁的任务被保留，结果是**出现一批重复任务**。同步日志里有提示，需要你手动清理。自动合并需要靠路径推断做映射，误判的代价比重复任务更高，所以没做。

- **开启两步验证后 APP 无法登录**。

  现象是死锁：开了 2FA 的账号在 APP 上输完用户名密码，屏幕上显示「请输入两步验证码」，**但整个页面上没有任何能输验证码的地方**。iOS 端从 `1.2.3` 起就是这样。

  > 根因在 APP 端。面板用 `401` + `two_factor_required` 承载两步验证挑战，这是一个「成功语义、4xx 载体」的中间态；而 APP 的网络层把所有 4xx 一律当失败就地抛异常，于是处理这个信号、把 `_needsTotp` 置真的那段代码整段成了永不执行的死代码，TOTP 输入框自然永远不渲染。同一个根因还连带害死了图形验证码分支。

  面板这一侧本轮做的是**契约加固**——不改 401 语义、只增字段、完全向后兼容：

  - 登录失败响应新增机器可读的 `code` 字段：`two_factor_required` / `invalid_totp` / `invalid_credentials` / `captcha_required` / `account_locked`。原有的 `error` 文案一个字都没改，现有客户端不受影响。
  - 两个 2FA 分支补回了 `captcha_required` / `captcha_id` / `require_after_failures`。它们此前是整个登录 handler 里唯一不带这组字段的失败分支，而图形验证码默认是每次登录都要过的——**这是修好 APP 之后的第二个阻断点**，不补的话第二次带验证码的请求仍然会卡住。
  - 「要求输入两步验证码」是中间态，不再被记成「登录失败」污染登录日志。验证码填错仍然照常记录。
  - `/api/v1/auth/login` 与 `/api/auth/login` 的登录限流改为各自独立计数。此前两个前缀共用同一个按 IP 计数的桶，手机和浏览器从同一个出口出去会互相挤占；而 2FA 每次登录要发两个请求，等效只剩下大约 2.5 次 / 分钟。

  > **必须把 APP 更新到 `v1.3.2` 才生效，只升面板没有用。** 面板侧的改动是为了让修好后的 APP 不再撞上第二个坑，它本身不能让旧版 APP 登录成功。
  >
  > 等不及发版的话，可以在服务器上执行 `ddp disable-2fa <用户名>` 先把该账号的两步验证关掉。

- **Magisk Debian 版安装时容器内 DNS 解析失败**。

  现象：rootfs 下载成功、容器探测通过，紧接着 `apt-get` 全部报 `Temporary failure resolving`，python3 / node / npm / git 一个都装不上，安装中止。Alpine 版不受影响。

  > **要说清楚的是：这一版没有证实根因。** 三个候选机制——老内核的 uid 网络门控、glibc 解析器并发查询丢应答、硬编码的那条 DNS 被网络屏蔽——都能导出同一句报错，而我们手上没有能复现的真机。所以本轮的做法是「补上判别手段，同时把互不冲突的低风险修复一起上」，不是「已解决」。

  本轮做的：

  - **安装日志新增判别探测**：在装依赖之前，容器内分别以 root 和 apt 的降权用户各跑一次域名解析，结论直接打进安装日志。下次再有人反馈，一眼就能定位是三个候选里的哪一个。
  - **容器 DNS 从单条硬编码改为多源**：宿主真实 DNS（最多取 2 条）+ 公共 DNS 补齐 + `options single-request-reopen`。glibc 会把 A 和 AAAA 两条查询用同一个源端口并发发出，不少家用路由和运营商 DNS 只回其中一条就把另一条丢了，只能干等超时重试——报出来的正是这句错。musl 不这么干，所以 Alpine 一直没事，这条能解释「同样的网络，只有 Debian 挂」。
  - **apt 加固**：补上 sandbox 用户、重试次数与超时配置。
  - **镜像源从硬编码单源改为四级回退**：南大 → 清华 → 阿里 → 官方，每换一个源就重跑一次 `apt-get update`。
  - **失败提示按「容器内 DNS 解析失败 / 镜像源不可达 / 下载中断」分流**。面板依赖管理里的失败提示也一并修了——它此前把解析失败一律归类成「请检查镜像源配置和宿主机网络连通性」，而宿主网络其实是通的，挂掉的是容器内解析，属于在向用户批量输出误诊。

  > **Alpine 版行为逐字节不变。** musl 会向所有配置的 DNS 并行发查询并采信第一个确定性应答（`NXDOMAIN` 也算确定性），给它配多条 DNS 反而可能在有强制解析器的网络上引入新的失败。所以这套只对 Debian 生效。

  > 本轮的 Magisk 改动**没有经过真机验证**，`Magisk/README.md` 里「Debian 版尚未经过真机验证」的声明仍然成立，是刻意保留的。如果你装了还是失败，把安装日志里探测结论那几行发出来，能直接定位。

- **`.git` 目录不再出现在脚本管理里**。

  现象上这只是「git 订阅拉下来的仓库，`.git` 整套文件跑到脚本文件树里了」。

  但它不只是显示问题：`.git/config` 里存着**被注入了访问令牌（PAT）的仓库地址**，此前可以通过脚本内容接口、下载接口以及 `ddp script cat` 直接读出来。能读到的主体比想象中宽——APP 令牌整体跳过角色校验，而且**每一个被执行的脚本**都拿得到面板令牌，也就是说第三方订阅仓库里的脚本能读到你别的订阅的令牌。

  现在 `.git` / `.svn` / `.hg` / `.bzr` 在文件树里隐藏，并且**读、写、删、改全部拒绝**，CLI 也一样。

  > 几条你会注意到的变化：
  >
  > - 仪表盘的「脚本文件数」会明显下降，因为此前把 `.git/objects` 里成千上万个对象文件都算进去了。**脚本没有丢。** 同理，子目录下的 `node_modules` 此前也被计入（旧实现只判相对路径的第一段），现在一并排除。
  > - 在面板里手改 `.git` 内文件的用法会消失——改远程地址、删 `index.lock` 解卡这类操作，现在只能到宿主机上做。
  > - 备份包里的 `.git/config` 会在打包时剥掉令牌，磁盘上的真实文件不动（动了后续拉取就没鉴权了）。**旧备份包里的令牌不做追溯清理**，曾经用令牌鉴权的 git 订阅建议轮换一次。

## 内部改动

- 模块外壳版本升到 `3`（Debian 容器 DNS 与 apt 加固）。`requiredMagiskShellVersion` 仍然是 `1`，所以**在线升级照常放行**——不会有人被挡在门外。

  但要说清楚：Debian 的 DNS 修复写在 `customize.sh` 里，那个脚本**只在刷 ZIP 时执行**。也就是说一键在线升级拿到的是「新面板 + 旧模块外壳」，DNS 与 apt 那套加固**拿不到**。想要这个修复，必须重刷一次模块 ZIP。刷过之后，后续版本仍然可以一键在线升级。

- 登录失败响应新增 `code` 字段（只增不删）。API 文档补齐了两步验证相关的字段与端点，并修正了此前把 `401` 一律描述成「Token 过期请重新获取」的错误契约说明——那正是把 2FA 信号吞掉的那套客户端逻辑的出处。

## 配套的 APP 版本

APP 同步发布 **`v1.3.2`**，修的就是上面第二条：开启两步验证的账号终于能在 APP 上登录，验证码分支也一并恢复。

**必须升级 APP 才生效，只升面板无效。**
