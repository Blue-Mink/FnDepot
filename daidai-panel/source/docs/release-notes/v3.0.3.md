# v3.0.3
<!-- release-title: Magisk 模块版支持面板内在线升级，PushPlus 可选发送渠道，依赖安装超时可配 -->

## 版本概览

`v3.0.3` 的主题是**把「只能这样」变成「可以选」**——三件此前被硬编码卡死的事，现在都由你决定。

Magisk 模块版不用再为了升个面板就重刷模块、重启手机、重下 300MB 依赖；PushPlus 不再只能发到微信公众号；依赖安装的 20 分钟超时不再是天花板。

## 新增

- **Magisk 模块版支持面板内在线升级**：进入「系统设置 → 概览 → 检查系统更新」，模块版现在会显示「Magisk 模块版在线升级」，点「立即更新」几十秒完成。

  它只替换三样东西：容器内的 `daidai-server`、`ddp` 和前端目录，同时写回模块目录并同步 `module.prop` 版本号，保证重启后不回滚。**容器 rootfs、apt/apk 装的系统包、Python venv 与已装依赖、`config.yaml`、`ports.conf` 一概不动，也不需要重启手机。**

  > 此前模块版在「检查更新」里会看到一段与 Android 完全无关的报错：「当前运行环境未提供 Docker CLI；精简镜像请配置 Watchtower 托管更新」，还建议你去宿主机敲 `docker compose pull`。根因是更新链路依次尝试 Watchtower → Docker → 二进制，模块版被二进制分支显式挡掉后，抛出来的却是 Docker 分支的报错。现在模块版有了自己的部署类型，排在 Docker 探测之前，这段误导彻底消失。

  两个例外仍然需要重刷模块 ZIP，面板会明确告诉你是哪一种：

  1. 某个版本改动了模块外壳（`service.sh` / `customize.sh` / rootfs 结构），并且新面板**根本无法**在旧外壳上运行。面板通过外壳版本号自检，不会把新面板硬装到不兼容的旧外壳上。

     > 自 `v3.0.4` 起补充说明：外壳只是**多了一项增量能力**时（例如 `v3.0.4` 的「停止面板服务」），在线升级照常放行，只有那一项功能会在面板里显示为禁用并提示重刷 ZIP。也就是说「改了外壳」不等于「必须刷 ZIP」。
  2. **从 `v3.0.2` 或更早版本升级**——在线升级能力本身要先随 `v3.0.3` 装上，所以这一跳必须刷 ZIP，之后才是一键在线。

- **Magisk 模块具备存活守护**：模块版此前没有任何 supervisor，面板进程一旦退出（崩溃、被系统杀、OOM）就只能重启手机才能恢复。现在后台守护每 60 秒探一次，不在就自动拉起。

- **PushPlus 可以选择发送渠道**：新增「发送渠道」下拉，覆盖官方全部 9 个渠道——微信公众号、App、浏览器扩展、第三方 Webhook、微信 ClawBot、企业微信应用、邮箱，以及消耗积分的短信和语音。选 Webhook 或企业微信应用时会出现「渠道编码」输入框。

  > 留空等于完全不发 `channel` 参数，行为与升级前逐字节一致，老配置不受任何影响。

- **依赖安装超时可配**：「系统设置 → 其它配置项 → 任务执行」新增「依赖安装超时(分钟)」，默认仍是 20 分钟，可调范围 5–720 分钟。

  > 触发场景是安装 `opencv-python` 这类在部分平台上没有预编译 wheel 的包：下载完 80MB 源码包后还要现场编译，ARM 设备上远超 20 分钟，此前会被固定阈值强杀，且日志停在下载完成那一行，看不出发生了什么。

## 修复

- **依赖安装日志弹窗不再谎报「已完成」**：日志流在长时间无输出后会被服务端收掉，而前端只看「日志流是否结束」就打上绿色的「已完成」标签——任务其实还在跑。现在标签读依赖的真实状态，日志流断开时明确提示「日志流已断开，任务可能仍在进行」。

  > 服务端一侧同时把「静默 5 分钟就结束日志流」改成了周期心跳，正常安装过程不会再被误判为结束。

- **通知发送不再把失败显示成成功**：面板此前只看 HTTP 状态码，而各推送服务在参数错误、额度不足、渠道未开通时普遍返回 `200` + 业务错误码。现在 PushPlus、Server酱、Bark、钉钉、企业微信机器人、飞书、Telegram 会校验业务码并回显厂商给出的错误原因。

  > 校验口径刻意保守：响应体不是 JSON、缺少约定字段、字段类型对不上时一律按成功放行，不会把本来能用的渠道改红。未核对过官方响应契约的渠道本次不动。

- **Debian 模块版在管理器里点「更新」不再被换成 Alpine 版**：两个 flavor 共用同一个模块 id，而 `updateJson` 只能填一个 `zipUrl`，所以「更新」按钮一直指向 Alpine ZIP——Debian 用户点下去，容器基础系统直接从 glibc 换成 musl，已装依赖全部失效。现在两个 flavor 各有各的更新地址。

  > 从 `v3.0.2` 升上来的 Debian 用户需要先手动刷一次 `v3.0.3` 的 Debian ZIP，之后管理器才会走对地址。

- **依赖「强制卸载」补上超时**：这条路径此前完全没有超时、也注册不了取消按钮，卡死会一直占着 apt / npm 的包锁，后续所有依赖任务都被堵住。现在与普通安装共用同一个超时配置。

- **依赖任务的临界点误判**：进程恰好在超时或取消触发的同一瞬间正常退出时，命令其实是成功的，此前会被无条件记成失败。

## 内部改动

- 通知渠道注册表新增 `channel` 与 `option` 两个字段。渠道表单是服务端 schema 驱动的，Web 端零改动即可渲染出下拉与条件输入框。
- `Magisk/service.sh` 的模块→容器同步改为「模块里的文件确实更新才覆盖」。这是在线升级的防回滚保险：模块目录写不进去时（KernelSU 下 `/data` 可能只读），容器内的新版本不会在下次开机被旧版覆盖。
- 面板在无法构建更新方案时也会回填当前部署形态，前端据此挑选正确的手动更新指引，不再对着非 Docker 部署提示 `docker compose`。

## 配套的 APP 版本

APP 沿用 `v1.3.1`，本轮不发新版。新增的「依赖安装超时(分钟)」属于服务端注册表配置项，若 APP 端设置页是硬编码表单，该项只在 Web 端可见。
